# 1.10.0 設定競合の比較・項目別解消と取消

対象日は2026年10月21日、基点は1.9.0の `e13b7ed`、作業ブランチは `feature/mobile-editor-and-master-maintenance` である。

## 事象と原因

利用者は設定競合の確認を表示した後、キャンセルしたと回答した。修正前の `syncSharedMaster` は競合確認の取消と、自動同期で確認できない場合に同じ通常Errorを投げる。手動同期はこれを「同期に失敗しました」と表示し、さらに「手動差分同期で解決」を案内するため、取消が故障のように見える。

手元とサーバーの設定は上書きされず保持されている。報告された費目・定期設定は既定マスタに存在せず、初回共有基点がない場合の差異も競合へ含まれ得る。ただし実際の両端設定を未取得であり、競合の誤判定とは断定しない。今回、基点推定・マージ規則・未指定値の正規化は変更しない。

## Phase 1 設計

1. マスタ競合を専用の内部エラー種別で識別し、確認の取消と確認待ちを区別する。同期入口はそれぞれ `master_conflict_cancelled`・`master_conflict` を返し、通信失敗の `lastError` に格納しない。通常の通信・署名・サーバー版競合の失敗は従来どおり例外とする。
2. 競合項目をSyncManagerの専用状態へ保持し、バッジに「設定の確認待ち」と表示する。明細だけの同期成功では消去しない。共有マスタの合成・承認送信・ローカル基点保存が成功したときに解除する。
3. 手動取消は「今回の設定競合の反映を取り消した」と表示する。直前の受信や明細送信は既に完了している場合があるため、同期全体をロールバックしたとは表示しない。再受信での取消も、完了済み送信・受信件数と残未同期件数を返す。
4. 自動同期では勝手に設定を上書きせず、確認待ちとする。再度の手動同期で同じ競合を確認し、承認したときだけ既存のローカル優先・サーバー版比較を使用して送信する。取消時は設定の両版と共有基点を保持する。
5. 取消分類だけの初期案はPatchの1.9.1であったが、比較・解消UIを追加した最終版はMinorの1.10.0である。規定5ファイルとpackage-lockを同期する。GASの通信契約は変更しない。

## テスト方針

単体・結合では自動競合、手動取消、設定原本と基点保持、明細だけの成功後も競合状態保持、承認による解除、実通信失敗、再受信での取消と既完了件数を捕捉する。UIでは両同期ボタン、取消の案内と確認待ちバッジ、再承認での解除を実ブラウザで検証する。既存の「取消で失敗」を期待するテストは新契約へ置換し、両版保持の検証は維持する。

## Phase 1 再入：競合を解消する手段の追加

利用者から「競合を解消する手段がない」と明示されたため、取消の表示修正だけでなく、項目別の比較・選択UIを追加する。新UIを伴う機能追加であり、最終版はMinorの1.10.0とする。先に記載した1.9.1は取消分類だけの初期案である。

- 各競合の手元・サーバー値を並べ、競合IDごとに採用側を選ぶ。全件手元・全件サーバーの補助操作は選択を設定するだけで、適用は別ボタンで行う。全項目選択前は適用できない。削除・未設定・null・空文字・空配列を区別する。
- `mergeMasterConfigs` の非競合合成は維持し、構造化した競合詳細を追加する。配列のIDは文字列のドット分割で扱わず、型付き経路で参照する。選択対象・側の過不足と危険キーを検証する。UIは辞書を返し、同期層が内部のMapへ変換する。
- 参照整合性は適用前に検証し、問題の設定名と項目をモーダル内へ表示する。選択を残して修正可能とする。親削除と定期設定保持などの矛盾は、設定送信・ローカル保存・共有基点更新の前に拒否する。
- 確認中にローカル共有値が変わった場合は選択を流用せず再確認を要求する。認証がロックされた場合も送信しない。別端末の更新は従来のサーバー版比較で検出する。
- ×・取消・Escape・ブラウザ戻る・認証ロックは待機Promiseをfalseで解決し、同期中状態を残さない。複数起動では古い結果を新画面へ適用しない。

詳細は `review49_merge.md` と `review49_ui.md` に記録する。基点推定と自動マージ規則は変更せず、利用者が比較して明示した競合だけを解決する。

## 認証境界の追加検証

独立レビューで、競合確認の取消後にロック済みDBから件数を復号する経路と、手動同期のfinallyがロック後も再描画する経路を点検した。競合結果は直近受信時点の件数を保持して返し、認証中は復号・画面再描画を行わない。比較画面のPromise終了とロック解除後の操作復帰を実SyncManager・暗号化DBのUIで検証する。

共有マスタのACK暗号化中に鍵が消去された場合は、平文フォールバックを保存しないよう、開始時のDMKと署名鍵の同一性を暗号化後・DB比較置換直前にも検査する。単体結合テストではロックを注入し、元の暗号化レコードと共有基点の無変更を検証する。この追加は独立した設計・テスト再承認を経て実装する。


## 表示と既存テストの横展開

参照IDの比較値は、各sideの元マスタで見つかる名称と元IDを併記する。中項目は計上・実態のそれぞれの親費目配下だけで照合し、別親の同一IDを混同しない。未知ID・null・削除は元の表示を保ち、表示用の名称をマージ結果や送信payloadへ混入しない。先行3件でREDを確認し、独立レビュー承認後に追加した。

全UI初回実行は185件中6件が失敗した。既存の編集open直後操作、集計ドリルダウン、固定sleep後の表示確認、遡及移動の要求待機を点検した。単独では合格し、DB遅延時には編集初期化前の操作やフィルタ値代入直後の旧一覧参照を再現した。待機を対象DOMの完了・対象要求のaction/id/dateへ置換するテスト側の修正を独立レビューで承認した。製品の期待値は緩和しない。


## 独立レビューと先行実行

実装とは別の `independent_review` が設計・テスト観点・実装をレビューした。解消helperは[review49_merge](review49_merge.md)、比較画面は[review49_ui](review49_ui.md)に記録する。

- 取消分類の先行テストはNode7件・UI3件の10件が旧実装で失敗した。既存期待値は取消通知へ置換し、両版保持を維持した。
- 項目別選択の結合7件も先行して全REDを確認し、pureの選択検査とUIの操作検証を独立承認後に実装した。
- 認証境界のテストでは、ACK暗号化中のロックによる平文書込をraw原本比較でREDとして捕捉した。送信直前の原本再読中の鍵変更も、サーバー原本変更のREDで確認し、送信前再検査を追加した。
- UIの実暗号化DB・SyncManager経路では、ロック後の復号による未処理rejectionを先行REDで確認し、件数キャッシュと認証中の描画抑止で是正した。
- 比較画面は実Chromiumの390px幅で撮影して目視した。参照IDだけの比較は名称とIDの併記へ改善し、side別の親参照と安全な文字列表示を先行テストで確認した。

## PRタイトル・本文草案

タイトルは `feat(sync): 設定マスタの競合比較・項目別解消を追加` である。

競合時に手元優先か取消しか選べず、取消も同期失敗として表示される問題を改善した。手動同期で各競合の両値と設定名を比較し、項目ごとに手元またはサーバーを採用できる。非競合の合成とサーバー版比較を維持し、参照不整合は画面内で修正できる。取消・認証ロック・確認中再編集では未確認の設定を上書きしない。

静的検査、全Node・UI実行結果と独立コードレビューを本記録へ記載する。既存から未達の全対象ファイルLine・Branch各97%以上という数値ゲートは、コード承認とは別に判定する。GAS通信契約は変更しておらず、クライアント1.10.0とPWAキャッシュを更新する。
