# 文書分割と既存テストの設計網羅性監査

## Phase 1 文書構成

基点は1.12.1のmain b547c13（PR #23反映済み）であり、docs/split-design-test-auditブランチで作業する。開始時e817c6fから作成したブランチを、作業中に反映された最新mainへfast-forwardした。元文書の本文はe817c6fと同一である。

旧system_design.mdを次の責務へ分割する。

- requirements.md: 目的・利用者の要求・業務制約・非機能要件である。旧3.x/4.xの識別子を維持し、DOM ID・クラス構成・保存手順の説明は設計へ移す。
- external_design.md: 画面・操作・入出力・確認/エラー・公開通信/JSON契約・外部から観測できる振舞いである。旧機能識別子に対応する見出しを持ち、既存の文脈図・ユースケース・画面遷移とJSON例を配置する。
- internal_design.md: 実装構成・計算/永続化/同期/暗号化・内部状態・排他/復旧・詳細シーケンス・ERD・実装上の制約である。
- system_design.md: 三文書への入口と旧章からの移行先を示す索引とする。過去レビューの記録は改変せず、現行README/開発プロセスの参照先を更新する。
- design_test_audit.md: 外部/内部設計の全見出しを識別し、テスト名・assert対象・確認範囲・未検証を対応付ける。ファイル名の一致やテスト合格だけで網羅済みと判定しない。

文書分割は既存要求の削除・未実装要求の実装済み化を意味しない。旧記述と現状の差は監査の仕様乖離として残す。今回は文書整備と既存テストの再確認であり、新機能実装や未検証の本番操作は対象外である。独立設計レビュー、既存テストの実assert調査、最終資料レビューを実施する。開発プロセスの文書改定Patch規定に従い版を1.12.2へ同期する。全対象各97%以上の数値ゲートは既存未達であり、文書整備のレビューとは分けて報告する。

## 分割・監査の実施

独立Phase2は基点の最新mainへの同期後にPASSである。外部設計64 ID、内部設計38 IDを実assertへ対応付け、旧3.x50節と4.x8節を要件側に保持した。旧JSON3例は意味を変更せず移動し、自己完結しない参照例であることを明示した。旧レビューの3.43/3.44リンクは索引にアンカーを保持した。README/開発プロセス/PRテンプレートは三文書と監査を参照する。

独立Phase5で前払補助情報等の旧ERD項目が欠落している指摘を受け、外部E-5.2へ現行正規形・旧フィールドの意味/型・未検証範囲を追補した。旧original_amount/parent_tx_idと現行total_amount/group_id+役割の違いを、現行が自動移行するという保証に置き換えない。ポイント相互参照、税、未入力/精算、カード補助も保持した。実装の深い検証不足は監査に残した。

## 既存テストの再実行

`npm test`は95スイート743件すべて合格し、失敗/取消/スキップ0件である。静的TAB・構文・型・GAS生成一致も合格した。Node測定はLine99.40%・Branch91.14%・関数96.71%である。ログは `/tmp/review54-final-node.log` である。

`npm run test:ui`は20スイート299件中298件合格・1件失敗、取消/スキップ0件である（`/tmp/review54-final-ui.log`）。既存`transaction_workflows.test.js:374`のexpense→transfer→income編集が、391行の共有チェック非表示で失敗した。対象単独実行は1件合格した（`/tmp/review54-existing-ui-probe.log`）。全体NGの全タイミングは未記録であるため単独の結果から原因を断定しない。

当該ケースは編集を再表示する際にactive/対象IDの確定を待っていない。読取を制御遅延させるprobeでは、非表示の旧DOMへselectを発火でき、後着openで元の振替が描画されチェックが非表示となる旧クリック失敗を再現した。active後に同操作を行うと成功した（`/tmp/review54-editor-ready-probe.mjs` と `.log`、pageErrors0）。今回は既存テストを変更しない網羅性監査であり、この待機不足を追加の監査結果とする。反復して合格した結果だけを採用せず、全体UIはNGとして残す。

全対象ファイルLine/Branch各97%以上の受入基準は既存から未達であり、今回のUI全体にもNGがある。コードレビューと文書分割の整合確認を、全テスト/数値ゲートの受入合格と同一視しない。業務コード/既存テストのassertは変更せず、ソースの差分は規定版情報のみである。
