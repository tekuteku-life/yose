# 1.11.0 セクション操作・編集分類・完全インポート

## 要求と原因

タイトル右端だけの開閉と編集の分類重複表示を改善する。手編集JSONの取込が部分的になる原因は、従来の明細updated_at比較と既存優先のマスタUnionである。差分方式は保持し、種別ごとの完全置換を追加する。利用者は「手元を置き換え、変更・削除を次回同期でサーバーにも反映」を明示選択した。

## Phase 1 設計

system_design 3.45を先行追加した。完全置換は全5種別に対応し、データ検証・原本比較・事前暗号化後の単一IDBトランザクションでローカル業務データとoutboxを保存する。セキュリティ鍵・settings・sync_baseは対象外である。マジックワードは「完全インポート」であり、単なるOK確認では実行しない。同期の多ファイル更新・中断再送・競合再承認はreview50_syncに記録する。UI2項目はreview50_uiに記録する。

ローカルDBはprepareReplacementImport(data)で検証済み計画（対象、更新後データ、比較するraw原本、開始時鍵）を生成し、commitReplacementImport(plan)で鍵・全raw原本を再確認して原子的に保存する。replacementはファイル種別外の業務値と送信済み共有基点を保持し、synced_passkey_bundleは持ち込まない。対象明細には取込時日時とunsyncedを付け、後続編集・通常ACK比較を可能にする。全データと明細取込ではローカル明細集合を置き換え、サーバー削除は専用actionが担う。

## テスト計画

先行Nodeテストは全5種別の置換、同時刻手編集と削除、対象外値・鍵・接続先・基点保持、不正型・危険キー・ID重複・不正参照の全書込前拒否、確認中変更・ロック・暗号化失敗・再取込の拒否、outbox比較更新・ACKを対象とする。ブラウザは既定差分、完全取込選択、誤マジックワード・取消・戻る、成功結果と再描画、保留の再承認と未処理例外を検証する。実IndexedDBのトランザクションrollbackをブラウザで検証する。

## Phase 1 / 3 再入：参照と認証境界

独立レビューに基づき、単体マスタ置換も保持される既存明細・定期・予算を含めた置換後全体の参照を検査する。暗号化await中のロック・鍵交換・同期開始による平文fallbackを拒否する先行ケースを追加する。戻る・再表示時ワード消去・版競合後の誤入力/取消/正確ワードによる明示再承認をUIで追加する。取込ACK成功時に限り、送信したマスタ種別の共有基点をaccepted masterへ保存し、現行マスタを変更しない。

## Phase 1 / 3 再入：休日調整と計上月

独立コードレビューで、実日付と計上月を一致必須にした検証が定期明細の月跨ぎ休日調整と矛盾すると判明した。実日付と計上月は独立した実在日・有効月として検証する。実生成関数により2026年10月末の休日調整で11月2日となる明細を生成し、JSON書出しから完全取込までの先行回帰ケースを追加する。サーバー側も同じ規則で検証する。

## Phase 1 / 3 再入：暗号化中の取消と取込ACK

独立レビューで暗号化待機中の戻る/ESCが計画を破棄してもcommitを止めない経路と、ACK後の取込明細がunsyncedのまま通常同期で再送される問題を指摘された。最終書込までモーダルのactiveと選択計画の同一性をsession条件に含める。ACKでは現行と送信時明細の内容が一致するものだけsyncedにし、後続編集と追加は未同期を保持する。過去締め明細・手編集スナップショットの完全取込直後に不要な再月締めを行わない。暗号化遅延中の戻る/ESC、取込版だけACK、実同期で再月締め不要の先行回帰を追加する。

## Phase 1 / 3 再入：手編集時の真偽値型

手編集したis_deleted等の文字列"false"がtruthyとして削除扱いになることを防ぐため、明細is_deleted/amount_pending、マスタis_archived/is_active/is_asset等の既知booleanは省略または真偽値だけを許可する。クライアントとサーバーの検証を一致させる。不正型は計画生成前に拒否して全原本を維持する先行テストを追加する。

## Phase 1 / 3 再入：検証の適用先

スナップショットのlast_closed_monthとmonthly_summariesのキーは有効月形式とし、送信時にしか分からない拒否をローカル確定前に捕捉する。真偽値型検査はキー名の全再帰ではなく各エンティティの既知フィールドへ限定する。年間予算の費目IDがis_activeであっても数値予算を正常に取り込めることを先行テストで検証する。

## Phase 1 / 3 再入：送信不能な保留の回復

単体マスタ取込では、手元に未取得のサーバー明細を含めた参照検査で送信を拒否される場合がある。既定の保留中再取込禁止は維持し、明示チェック「送信待ちを新しい完全インポートでやり直す」を選んだ場合だけ、新ファイルをmagic最終確認して保留を置き換える。旧要求が既にサーバーへ適用済でも巻き戻しではなく、新しい取込IDで改めて完全置換する。旧保留の原本を含めCASし、同ID内payloadは不変とする。取消・誤ワード・古いACK・確認中の保留変更は新保留を誤って確定/消去しない。
