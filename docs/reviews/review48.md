# Android受信失敗の追加調査とGAS公開設定の整合

2026年10月21日の追加情報は「同期に失敗しました:受信:fail to fetch」、環境はAndroidである。[review47](review47.md)の未コミット・未公開の1.9.0改修と同じブランチ内で是正する。公開済み1.9.0への別パッチではないため、バージョンは1.9.0を維持する。

## 調査と切り分け

- 受信段階では署名付きPOST `fetch_state` を送信する。HTTPエラー・GASのJSONエラーとは別に、ブラウザのfetch拒否が報告されている。Androidのブラウザ名、HTTP応答、CORSログ、実デプロイ設定は未確認である。
- 調査時の `gas/appsscript.json` は `webapp.access: ANYONE` であった。[Google公式仕様](https://developers.google.com/apps-script/manifest/web-app-api-executable)ではGoogleログイン済みの利用者が対象である。一方、同期はログインCookieを送らない設計である。Googleログイン不要の公開値は `ANYONE_ANONYMOUS` であり、ソース設定の不整合を確認した。
- この不整合はAndroid固有の問題ではない。本番設定がソースと一致するかは未確認であり、報告された障害の根本原因と同一とは断定しない。CORS・リダイレクト・接続制限・URL違いなどの可能性は残る。

## Phase 1 設計

READMEのマニフェスト例とsetup案内も含め、公開前の `USER_PUBLIC_KEYS` 登録を維持する。初回自己署名のwrite-onceは登録競合を防ぐだけで最初の所有者を証明しないため、公開前のキー設定を省略する根拠にしない。公開設定を `ANYONE_ANONYMOUS` とし、実行主体 `USER_DEPLOYING` と最小OAuthスコープを維持する。署名付きPOST、時刻検証、write-onceの初回公開鍵登録は変更しない。接続確認GETは固定ステータスだけであり、家計データを返さない。setup手順では「Googleログイン不要」と明示する。

設計2.4・4.2へ先行反映した。ソース変更だけで既存公開設定を変更できるとは扱わず、再デプロイとアクセス設定の確認が必要である。外部の本番設定は変更しない。

## Phase 3 先行テスト方針

- デプロイが匿名到達可能であり、owner実行・OAuth最小化を維持することを検証する。
- マニフェストがログインを要求する場合はブラウザ到達失敗を返す境界fixtureを使用し、Cookieなしの署名付き双方向同期を実GASモック経路へ流す。これは公開ゲートのモデルであり、実Google環境の再現ではない。
- 匿名到達可能でも未署名POSTは拒否され、データが変更されないことと、GETが固定ステータスだけを返すことを検証する。

利用者はAndroidのシークレットタブで同じ `/exec` URLへアクセスし、`status: ok` のJSONが返ることを確認した。このGET到達確認により実公開設定がGoogleログインを要求する可能性は低下した。マニフェスト修正は独立した設定整合の是正であり、今回の障害解消とは扱わない。その後、利用者は約1.8秒の `doPost` が2回記録され、Android側も正常完了したことを確認した。GET成功だけではクロスオリジンのPOST・リダイレクト応答の読取成功を保証しない。
