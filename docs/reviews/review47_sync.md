# Review 47 同期・マスタ反映設計

## Phase 1 調査結果

- マスタ変更後の `saveMasterConfigAndSync` はGASへの送信完了を待ってから画面再描画するため、通信時間が操作の待ち時間となる。
- 手動差分同期は明細と残高だけを対象とし、設定マスタは別ボタンで送受信するため、機能が分断されている。
- 同期バッジは明細未同期件数しか参照せず、進行中状態と設定の未送信を表現できない。
- 通信は既に `text/plain` であり、コードだけから本番の fetch error 原因を断定できない。本番操作は行わず、通信失敗を再現テストで捕捉し、URL・公開権限・接続を確認できるメッセージへ改善する。`no-cors` による応答隠蔽や変更要求の自動再送は行わない。

## Phase 1 設計

1. 手動差分同期を明細・残高・共有マスタの統合入口とする。既存の排他区間内で受信、マスタ調停と送信、明細送信、再受信を実行する。設定専用の送信・取得ボタンとイベント処理を削除する。
2. マスタの前回共有版を既存の `master_config` ストアの別キーへDMKで暗号化して保存する。端末固有の `theme`、`collapsed_panes`、旧パスキー関連データ、`updated_at` は共有対象外である。
3. 初回共有版がない場合、サーバーが初期状態なら空設定を基準とする。それ以外はアプリの既定マスタを基準とし、既存データが双方異なる場合は通常の競合確認を要求する。前回共有版・現在ローカル・現在リモートを三方向比較する。IDをもつマスタ配列はID単位、オブジェクトは項目単位、IDをもたない配列は値集合単位で双方の非競合変更を保存する。双方が同じ値へ変更した場合も競合としない。削除対変更は親項目で競合として扱い、同IDの別属性変更は合成する。双方に順序変更がある場合はローカル順序を優先し、リモートのみのIDを末尾へ追加する。親削除と子変更は親全体の競合として承認を要求する。合成で生じる口座引落先、定期ルールの口座・費目・中項目参照の欠落を送信前に検証し、参照切れでは保持してエラーとする。
4. 同一項目の異なる変更は自動送信せず、ローカルとリモートを保持する。手動同期時に競合項目を明示し、ローカル優先で送信するか確認する。取消と自動同期では保存内容を上書きしない。再試行時に再度確認できる。
5. サーバーへのマスタ送信には取得時の共有版の正規化文字列を `base_version` として付与し、ロック区間内で一致確認してから保存する。他端末の途中変更を検知した場合は再取得を促し、ローカル変更を保持する。
6. ローカルへの受信反映は現在版と共有基準版の両キーを同一IndexedDB transactionで比較置換する。通信中にローカル編集があった場合は送信前ローカルを基準に受理済みマスタと再編集版を再合成し、再編集を優先して保持する。再編集と受理済み基準を原子的に保存するため、クラッシュやCAS不一致で共有版だけが前進することはない。
7. マスタ編集はローカル保存と画面反映を完了してから背景同期を開始する。通信未設定・オフライン・認証ロック・失敗時もローカル保存を維持する。背景処理中にさらに保存された場合は、終了後に新しい未同期版を処理する。
8. 通信はAbortControllerにより30秒で打ち切り、タイムアウトと到達失敗を区別する。サーバー側で処理が完了した可能性があるため自動再送せず、手動再試行は必ず再取得から開始する。
9. `SyncManager` の進行状態を購読可能にし、同期中はヘッダーバッジへ `同期中…` と `aria-busy` を表示する。完了後は明細未同期件数と共有マスタの未同期有無を再集計する。手動ボタンは処理中に無効化する。

## Phase 3 テスト観点案

- マスタのみ変更・受信のみ・双方向異ID変更・同ID別属性・同値変更・同属性競合・競合承認取消・再承認。
- 初回同期の既定値と既存データ、端末設定の保持、暗号化共有版、未同期判定。
- サーバーCAS拒否、通信失敗、HTTP失敗、JSON失敗とローカル保持、同期中再編集と再試行。
- 通信のsimple request維持、GASデプロイURLの誤りと通信失敗の説明、無断再送がないこと。
- 同期開始・成功・失敗・排他・自動同期の状態通知、バッジの進行状態とマスタ未同期表示。
- UIの設定即時反映と背景処理中操作、統合手動同期、廃止ボタン不在。
