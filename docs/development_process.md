# 開発プロセス定義書 (Development Process Definition)

本書は、「よせあつめ家計簿 (Yoseatsume Kakeibo)」プロジェクトにおける機能追加、仕様変更、および保守開発における標準開発プロセスと品質ゲートを定義する。

---

## 1. 基本方針 (Guiding Principles)

1. **全体最適と「あるべき姿」の追求**:
   - 局所的・場当たり的な変更（モグラ叩き的なワークアラウンドや不要な互換パッチ）を厳禁とする。
   - 変更要求が発生した際は、必ずシステム全体（アーキテクチャ、データフロー、セキュリティ境界、UI/UX）を俯瞰し、システム自体が最もシンプルかつ堅牢となる「あるべき姿 (To-Be Architecture)」を定義してから着手する。
2. **仕様先行（Design-First）およびテスト駆動（Test-Driven）**:
   - コードを変更する前に、必ず設計書を更新し合意を形成する。
   - 実装前にテストを用意し、検証観点の網羅性を担保する。
3. **独立サブエージェントによる厳格な品質ゲート**:
   - 設計段階、テスト設計段階、最終受入段階の各ゲートにおいて、独立した「Gemini 4 Argon」サブエージェントによる客観的な多角的レビューを必須とする。
4. **ブランチ保護とプルリクエスト運用**:
   - `main` ブランチへの直接コミットを禁止し（プロセス定義自体の特別更新等を除く）、必ずトピックブランチからプルリクエスト（PR）を経由して変更を統合する。
   - PRには規定のテンプレートを用い、設計判断、テスト結果、Argonサブエージェントのレビュー記録を日本語で明記する。
5. **手戻り発生時の全手続き再実行原則 (Mandatory Rework & Gate Re-entry)**:
   - 開発プロセスの途中（設計・テスト・実装・レビュー中）において、サブエージェントレビューの指摘やユーザー指摘により手戻り（仕様変更、設計見直し、不具合修正）が発生した場合、修正箇所のみの局所的対応で済ませることを厳禁とする。
   - 影響を受ける最上流フェーズ（Phase 1 設計 または Phase 3 テスト）まで遡り、設計書更新、テスト観点拡充、実装、不要コード排除、および各フェーズの品質ゲート・レビューを**最初からすべてやり直す**。
6. **完了後不具合の横展開調査・テスト捕捉・再レビュー原則 (Post-Completion Bug Analysis & Test Regression Protocol)**:
   - すべてのプロセスが完了（またはPR作成後・マージ直前）した段階で、ユーザーからの指摘や不具合が発覚した場合:
     1. **原因究明と横展開調査**: 単一事象の局所修正にとどまらず、根本原因を究明し、システム全体（フロントエンド、バックエンド、DB、暗号層）に類似の不具合や波及リスクがないかを徹底的に点検・確認する。
     2. **テスト側の修正・捕捉強化**: 発覚した不具合および潜在的な類似パターンを、自動テスト（単体・結合・システム）で確実に検知・再現・捕捉できるようにテストコードを修正・拡充する。
     3. **検証とレビューの再実行**: 修正したテストを含む全テストの100%パスおよびカバレッジ基準達成を確認し、独立したArgonサブエージェントによる品質ゲートレビュー（Phase 5）を再度実施して承認記録を更新する。
7. **厳格なテストカバレッジ基準 (Coverage Threshold >= 97%)**:
   - テストカバレッジ基準は、**全対象ファイルにおいて命令網羅（Line Coverage）$\ge 97\%$ かつ 分岐網羅（Branch Coverage）$\ge 97\%$** を必須とする。
8. **タブインデント規約と自動チェック (Tab Indentation Standard: Tab = 4 Spaces)**:
   - すべてのコードファイル（JavaScript, GAS, HTML, CSS, JSON, Shell）におけるインデント文字は、**タブ文字 (`\t`)** を使用する。
   - 表示幅は **4スペース相当 (Tab Width = 4)** をプロジェクト標準とする。
   - 半角スペースによるインデントやスペースとタブの混在は静的リントで厳禁とし、`npm run lint:indent`（`scripts/check_indent.js`）を設けて自動チェックを必須化する。
   - プロジェクトルートに `.editorconfig` を配備し、各開発エディタでの設定差異を排除する。
9. **実装後の構文エラーチェック自動検証 (Post-Implementation Syntax Error Check)**:
   - プロダクションコードおよびテストコードの実装・修正直後に、静的構文チェック（`npm run check:syntax`）を実行し、JS/GAS/JSON等の構文エラー（`SyntaxError`、構文崩れ、未定義識別子、括弧不整合等）を自動検証・即時排除する。
10. **実装後の独立コードレビュー原則 (Post-Implementation Independent Code Review)**:
   - 実装完了後、独立サブエージェント（Gemini 4 Argon）による実装後コードレビュー（Code Review）を必ず実施する。
   - 単なるテスト通過確認にとどまらず、プロダクションコードの品質・安全性・クレンリネス、および「不足する設計、実装、テストがないか」の網羅性を厳しく精査する。

## 2. 開発ライフサイクル・標準フロー (Development Workflow)

```mermaid
flowchart TD
    B0["作業ブランチ作成 (feature/*, fix/*)"] --> P1["Phase 1: 設計変更・あるべき姿の策定"]
    P1 --> P2["Phase 2: Argonサブエージェント設計＆セキュリティレビュー"]
    P2 -->|指摘事項あり / 仕様再検討| P1
    P2 -->|承認 & docs/reviews/に記録保存| P3["Phase 3: テスト実装 & Argonテスト観点レビュー"]
    P3 -->|テスト観点不足| P3
    P3 -->|テスト承認| P4["Phase 4: 機能実装・不要コード削除 & 構文エラーチェック"]
    P4 --> P5["Phase 5: Argonサブエージェント実装後コードレビュー (不足観点点検) & 最終受入ゲート"]
    P5 -->|不合格 / 実装・構文指摘| P4
    P5 -->|テスト不足 / 観点漏れ| P3
    P5 -->|仕様・設計不足 / 設計起因の指摘| P1
    P5 -->|合格 (Grade A+)| P6["Phase 6: 英語コミット & プルリクエスト発行 (日本語フォーマット)"]
    P6 --> U1{"ユーザー確認 / 指摘・不具合発覚?"}
    U1 -->|指摘あり| P7["完了後是正プロトコル: 類似不具合の横展開点検 & テスト捕捉拡充"]
    P7 -->|設計起因の修正| P1
    P7 -->|実装・テスト起因の修正| P3
    U1 -->|承認| P8["CI合格・マージ・ブランチ整理"]
```

---

### ブランチ作成 (Branch Creation)
- 作業開始前に必ず最新の `main` ブランチから機能・修正単位の作業ブランチを作成する。
- 命名規則:
  - 新機能追加: `feature/<feature-name>`
  - 不具合修正: `fix/<issue-name>`
  - リファクタリング: `refactor/<target-name>`
  - ドキュメント整備: `docs/<doc-name>`

---

### Phase 1: 設計書の変更と「あるべき姿」の策定
1. **全体影響の分析**:
   - 新規要件・修正要求に対し、フロントエンド（PWA/IndexedDB）、バックエンド（GAS/スプレッドシート）、暗号層、同期プロトコルの全体影響範囲を洗い出す。
   - 既存の仕様や制限（Google OAuthスコープ、40k文字セル制限、Ed25519暗号検証など）との整合性を確認する。
2. **設計書の先行更新**:
   - [docs/system_design.md](system_design.md)（および関連仕様書）を更新する。
   - 必要に応じて、データフロー図（DFD）、シーケンス図、ERD、状態遷移図を更新・追記する。
   - 部分的な継ぎ接ぎではなく、システム全体として最も自然で簡潔な設計となっているかを確認する。

---

### Phase 2: Argonサブエージェントによる設計・セキュリティレビュー
1. **サブエージェントの召喚**:
   - モデルに **Gemini 4 Argon** を指定した独立サブエージェント（Role: `Security & Architecture Auditor`）を起動する。
2. **レビュー観点**:
   - **ソフトウェア開発・アーキテクチャ観点**:
     - 単一責任原則、疎結合性、状態管理の妥当性
     - オフラインファーストおよびゼロコスト運用の継続性
     - データモデルおよび同期プロトコルの整合性
   - **セキュリティアセスメント観点**:
     - STRIDE脅威分析（なりすまし、改ざん、否認、情報漏洩、DoS、権限昇格）
     - OWASP Top 10（インジェクション、XSS、暗号の不備、認証・認可）
     - OAuthスコープ最小化（`@OnlyCurrentDoc`）の維持
     - 秘密鍵ライフサイクル（平文非保持、PIN暗号化、メモリ自動消去）
3. **レビュー記録の保存**:
   - `docs/` 直下が散らからないよう、専用の `docs/reviews/` ディレクトリ配下にレビュー記録を格納・管理する。
   - レビュー結果、指摘事項、残余リスク、判定スコアを `docs/reviews/review<連番>.md`（例: `docs/reviews/review1.md`, `docs/reviews/review2.md`）として保存する。
   - 指摘事項がある場合は Phase 1 に戻り設計を改善する。

---

### Phase 3: テスト実装とテスト観点レビュー
1. **テストコードの実装**:
   - 設計書に基づき、単体テスト（`test/unit/`）、結合テスト（`test/integration/`）、システムシナリオテスト（`test/system/`）を作成・拡充する。
   - 正常系、異常系、境界値、並行性、エラーハンドリングを網羅する。
2. **Argonサブエージェントによるテスト観点レビュー**:
   - Gemini 4 Argon サブエージェントにより、テスト観点の抜け漏れ（エッジケース、タイムスタンプ異常、ネットワーク切断、不正ペイロード、暗号攻撃等）がないかレビューを受ける。
   - 指摘された不足ケースを追加実装する。

---

### Phase 4: 機能実装・構文エラーチェック・不要コード削除
1. **プロダクションコード実装**:
   - 設計およびテストに適合するよう、最小限で堅牢なコードを実装する。
2. **実装後の構文エラーチェック（必須ゲート）**:
   - 実装・修正完了直後、テスト実行やレビュー依頼へ進む前に `npm run check:syntax`（`node scripts/check_syntax.js`）を実行する。
   - JavaScript（`node -c`）、Google Apps Script（`vm.Script`）、JSON（`JSON.parse`）の構文エラー（`SyntaxError`、未定義シンボル、閉じ括弧不足等）が **0件** であることを自動検証する。
   - 構文エラーが1件でも検出された場合、テスト実行やレビュー依頼を行わず即座に修正する。
3. **コードのクリーンアップ・棚卸し（必須ステップ）**:
   - **不要コードの削除**: 新実装により使われなくなった関数、変数、import、CSSルールを完全に削除する。
   - **不要な互換性維持コードの排除**: 過去の暫定対応や、古いデータ構造を維持するための場当たり的なフォールバック・冗長分岐を点検し、現行仕様（Schema v2等）に統一して不要な分岐を削除する。
4. **インデント・フォーマット検証**:
   - `npm run lint:indent` を実行し、全コードファイルがタブインデント（表示幅4スペース）に準拠していることを検証する。

---

### Phase 5: Argonサブエージェントによる実装後コードレビュー & 最終受入ゲート
1. **品質基準および全テストの検証**:
   - 静的チェック（`npm run lint` = `lint:indent` + `check:syntax`）のエラーが 0 件であること。
   - 全自動テスト（単体・結合・システム）が 100% 合格すること。
   - カバレッジ基準: **全対象ファイルで命令網羅（Line）$\ge 97\%$ かつ 分岐網羅（Branch）$\ge 97\%$** を満たしていること。
2. **実装後コードレビュー（Code Review）の実施**:
   - モデルに **Gemini 4 Argon** を指定した独立サブエージェント（Role: `Senior Release & Security Gatekeeper` 等）を召喚し、実装コード差分の精査を実施する。
   - **不足する設計・実装・テストの網羅性チェック**:
     - 設計の不足（考慮漏れ、アーキテクチャ境界の曖昧さ、非機能要件の欠如）がないか。
     - 実装の不足（エッジケース未処理、例外処理漏れ、入力バリデーション漏れ、UI状態の不整合）がないか。
     - テストの不足（正常系のみで異常系・境界値・セキュリティ回帰テストが漏れていないか）がないか。
   - **Mermaid図の構文検証**:
     - レビュー報告書内に Mermaid による図示を含める場合は、特殊文字のエスケープや記法を点検し、構文エラーチェックを必ず実施する。
   - 指摘事項がゼロ（Grade A+ 承認）となるまで完了とみなさない。

---

### Phase 6: コミットとプルリクエスト発行 (Commit & Pull Request)

1. **Gitコミットメッセージ（英語記述）**:
   - 最終レビュー合格後、コミットメッセージは**英語（English）**で記述する。
   - 形式: Conventional Commits (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`)
   - 必須記載内容:
     - 変更要約（Short Summary）
     - 改修の背景と目的（Rationale & Context）
     - 主な変更点と設計判断（Key Changes & Architecture Decisions）
     - セキュリティ対策およびテスト結果指標（Security mitigations & Test coverage metrics）
2. **プルリクエストの発行（日本語フォーマット）**:
   - リポジトリ規定のテンプレート（`.github/pull_request_template.md`）を使用し、**日本語**で以下を記述してPRを発行する:
     - **背景**: 要求事項、改修の目的、課題
     - **変更内容（設計・ファイル）**: システム全体のあるべき姿に基づいた設計判断、追加・変更・削除ファイル一覧
     - **確認内容**: 動作確認・設計整合性・不要コード削除・セキュリティ確認チェックリスト
     - **テスト結果**: 全自動テストの実行結果およびカバレッジ測定結果（全ファイル97%以上）
     - **レビュー結果**: `docs/reviews/review<連番>.md` へのリンク、担当したArgonサブエージェント名、判定ランク、指摘事項と対応状況
3. **PRマージ基準**:
   - CIによる自動テスト全パス（カバレッジ全対象ファイル97%以上）
   - Argonサブエージェントによるレビュー合格記録（Grade A+）の添付
   - チェックリストの全項目充足
4. **マージ後のブランチ整理 (Branch Cleanup)**:
   - PRマージ完了後は、リポジトリのブランチ乱立を防ぎ健全性を維持するため、トピックブランチ（リモートおよびローカル）を速やかに削除する。

## 3. 手戻りおよびユーザー指摘発生時の運用規定 (Rework Protocols)

### 3.1 開発途中の手戻りプロトコル (In-Development Rework Protocol)
- 開発プロセスの各フェーズ（Phase 1〜5）進行中に、Argonサブエージェントの指摘やユーザーレビューによって手戻りが発生した場合:
  1. **波及最上流へのロールバック**: 手直し箇所が設計に関わる場合は Phase 1、テスト仕様に関わる場合は Phase 3 へ遡る。
  2. **手続きの完全再実行**: スキップやショートカットは一切認めず、設計書更新 $\rightarrow$ 設計レビュー $\rightarrow$ テスト実装・拡充 $\rightarrow$ テスト観点レビュー $\rightarrow$ 実装・クリーンアップ $\rightarrow$ 最終受入レビューの全ゲートを最初からやり直す。

### 3.2 プロセス完了後の不具合修正プロトコル (Post-Completion Bug Analysis & Test Catching Protocol)
- プルリクエスト作成後やリリース直前の最終確認フェーズ等、一通りの開発プロセスが完了した後にユーザー指摘等で不具合や修正事項が発生した場合:
  1. **類似不具合の水平展開点検 (Horizontal Inspection)**:
     - 発覚した事象を単体のバグとして局所修正するだけでなく、「なぜその不具合が発生したか」「類似の処理パターン（非同期処理、DBトランザクション、暗号複合化、状態管理、UIバインドなど）が他モジュールに存在しないか」をシステム全体にわたって水平展開点検する。
  2. **テスト捕捉強化 (Test Catching & Coverage Extension)**:
     - 発見された不具合、および点検で洗い出された潜在的な類似パターンが、自動テストスイートで確実に赤（Fail）となり検知・捕捉できるようにテストケースを修正・拡充する。
     - テストの修正が完了した後にプロダクションコードの修正を適用し、テストが緑（Pass）になることを確認する（TDDによる再発防止の担保）。
  3. **検証・カバレッジ・再レビュー (Verification & Re-review Gate)**:
     - カバレッジが全ファイルで **97%以上** を満たしていることを確認する。
     - 独立した Gemini 4 Argon サブエージェントによる総合レビュー（Phase 5）を再度実施し、新たな監査レポート（`docs/reviews/review<連番>.md`）として記録を残して承認を得る。

### 3.3 カバレッジ97%基準の運用指針 (Coverage Threshold Operational Guideline)
- **命令網羅（Line）$\ge 97\%$ かつ 分岐網羅（Branch）$\ge 97\%$** を満たすにあたり、到達不能な防御的例外分岐に対して無理にモックテストを作成して数値を繕うことは厳禁とする。
- 過去の暫定対応、不要な古い互換コード、未使用のフォールバック分岐をPhase 4.3（クリーンアップ・棚卸し）において徹底的に削除（母体分岐数の削減）することで、シンプルで無駄のないアーキテクチャと共に高カバレッジを達成すること。

## 4. コードスタイル・インデント規約詳細 (Code Style & Formatting Specification)

### 4.1 タブインデント基準
- **インデント文字**: タブ (`\t`) 1文字につき論理インデント1レベルとする。
- **表示幅 (Tab Size)**: 4 spaces (`tab_width = 4`, `indent_size = 4`)。
- **対象ファイル範囲**:
  - フロントエンド: `js/**/*.js`, `sw.js`, `index.html`, `css/**/*.css`, `manifest.json`, `version.json`
  - バックエンド: `gas/**/*.gs`, `gas/**/*.json`
  - テスト・ツール: `test/**/*.js`, `scripts/**/*.js`, `package.json`
- **スペースインデントの禁止**:
  - 2スペースや4スペースなどの半角スペースによるインデント、およびタブとスペースの混在（Mixed tabs and spaces）を禁止する。
  - **例外事項**: JSDoc等のブロックコメント継続行における ` *`（アスタリスク前の単一スペース、例: `\t * ...`）のみ許容する。

### 4.2 自動チェックと開発環境の統一
- **静的リントスクリプト**:
  - `scripts/check_indent.js` をリポジトリに配備し、`package.json` の `npm run lint:indent` で全コード対象の静的チェックを実行可能とする。
  - `npm test` の前提タスクとしても統合されており、インデント違反が存在する場合はテスト実行前に即時エラーで停止する。
- **EditorConfig によるエディタ設定統一**:
  - プロジェクトルートに `.editorconfig` を配備し、主要エディタ（VS Code, JetBrains, Vim等）でファイル保存時に自動的にタブ（表示幅4）が適用される環境を整える。

## 5. レビュワー（Argonサブエージェント）への指示・プロンプト規定 (Reviewer Directives & Prompt Specification)

開発プロセスにおいて独立サブエージェント（Gemini 4 Argon persona）にレビューを依頼する際は、以下の指示をプロンプトおよび評価観点として必ず含めること。

### 5.1 不足する設計・実装・テストの網羅性チェック（Gap Analysis）
- レビュワーは単に提出されたコードやテストが動くかを確認するだけでなく、要求仕様および「あるべき姿」に対して以下のような**抜け漏れ・不足観点がないか**を徹底的に洗い出し、厳格に判定すること：
  1. **設計の不足**:
     - 非機能要件（PWAオフライン動作、メモリ鍵管理、暗号化境界、キャッシュ整合性）の考慮漏れはないか。
     - 将来的な拡張性やスケーラビリティ、不要な依存関係・循環参照が残っていないか。
  2. **実装の不足**:
     - 異常系・エラーパス（JSONパース失敗、ネットワーク切断、タイムアウト、不正データ入力）の例外処理が漏れていないか。
     - 境界値（0件データ、空文字、上限値、極端な数値）に対する防御処理が漏れていないか。
     - XSS対策（`escapeHtml`）、Prototype Pollution対策（`__proto__` 拒絶）等の安全対策が漏れていないか。
  3. **テストの不足**:
     - 実装されたすべての機能・分岐に対して、正常系だけでなく異常系・境界値のテストケースが存在するか。
     - 回帰テストとして機能するよう、想定される不具合パターンを確実に捕捉・検知できるテストになっているか。
- いずれかに不足が認められる場合は、妥協せず差し戻し（Changes Requested / Phase 1 または Phase 3 へのロールバック）を指示すること。

### 5.2 レビュー結果におけるMermaid図の構文エラー検証
- レビュー報告書（`docs/reviews/review<連番>.md`）やドキュメント内に Mermaid（`flowchart`, `sequenceDiagram`, `stateDiagram` 等）による図示を含める場合は、**必ずMermaid構文エラーチェックを行うこと**。
- **Mermaid構文遵守ルール**:
  1. **ノードラベルのクォート**:
     - ノードラベル内に丸括弧 `( )`、角括弧 `[ ]`、波括弧 `{ }` などの記号が含まれる場合、必ずダブルクォートでラベル全体を囲むこと（例: `id["Process (Step 1)"]`）。クォートを怠ると Mermaid パーサーが形状指定トークンと誤認して構文エラーとなる。
  2. **シリンダーノードの内部クォート**:
     - データベースやストレージを表すシリンダーノード `id[(...)]` では、内部文字列をダブルクォートで囲むこと（例: `DB[("IndexedDB: AES-GCM-256")]`）。
  3. **矢印・接続線の記法遵守**:
     - `-->|ラベル|` や `-.->` などの正規の矢印記法を用い、不正な矢印トークンや未対応のHTMLタグを使用しないこと。
  4. **自動検証の実行**:
     - レビュー報告書作成後、`npm run check:syntax`（`scripts/check_syntax.js`）を実行して Mermaid 構文エラーが検出されないことを確認すること。

### 5.3 セキュリティ・コード品質・規約遵守の精査
- STRIDE脅威分析に基づくセキュリティ堅牢性の評価。
- TABインデント規約（タブ幅4スペース、`\t`）の完全順守。
- 一時的ワークアラウンド、不要な過去互換コード、残存デバッグログ（`console.debug`, `debugger` 等）の完全排除。
